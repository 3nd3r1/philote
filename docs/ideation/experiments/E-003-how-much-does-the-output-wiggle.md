## Steps

1. Count output lines: copied from the base, generated by templates, written by the model. Free.
2. Make small spec edits, rebuild with `--frozen`, and count the files and lines that change, or the nodes that need the model again. Free.
3. Build neighbr twice from an empty lock and diff the two outputs. That's the wiggle with no pinning. Costs model calls.
4. Give Claude Code a SPEC.md for the same app, twice in fresh repos, and diff the two results. Then make one feature change both ways and compare diff sizes. Costs a lot of model calls.

## Kill criteria

- Step 3 differs about as much as step 4. Pinning would then be the only thing philote adds, and a lockfile around an agent might do the same.
- Step 2 keeps finding edits that rebuild nodes they don't touch, and Q-019-style fixes can't stop it.

## Progress

**2026-11-12, steps 1 and 2.** neighbr builds 2885 lines. 1234 are generated rather than copied from the base, and 175 of those (14%) are written by the model. The rest are templates.

| Edit | Result with `--frozen` |
| --- | --- |
| Change a page's `empty` text | 1 file, 2 lines |
| Add a form page | 4 files, 7 lines, no model |
| Add an action to HorseCard | 4 files, 15 lines, no model |
| Change HorseCard's `shows` | HorseCard needs the model, nothing else does |
| Change a step's intent | that step needs the model |
| Add a field to Horse | **both steps** need the model |

The last row is a leak: every step's prompt lists every entity's type, so any data change invalidates every step, even `match_if_mutual`, which never takes a Horse. Q-019 asks what a step's prompt should include.

**2026-11-13.** D-022 closes the leak: with declared tables, adding a field to Horse needs the model for `record_swipe` only, which takes a Horse. Steps 3 and 4 run next.

**2026-11-13, step 3.** Two builds of neighbr from an empty lock, both with claude-opus-5-5. Each is 2913 lines. 94 lines differ, all of them in the five model-written bodies. Every template line is identical. The bodies themselves wander: of about 183 model-written lines per build, 89 are the same in both. The steps differ in style, like `return insert(...)` against `const row = insert(...); return row`. The components differ more, because their `look` leaves room. With the lock, the same spec gives 0 differing lines.

**2026-11-13, step 4.** Claude Code (claude-opus-5-5, the same model) built neighbr twice from a SPEC.md that says in prose what the spec says, in fresh repos with npm and file tools allowed. Both builds worked and typechecked.

They differ in behavior too, not just in style: the API port, whether unknown request fields are refused, and whether `POST /swipes` also makes matches.

Then the same change both ways: horses get a `color`, editable in the forms and shown on the profile.

| | Philote | Claude Code, run 1 | Claude Code, run 2 |
| --- | --- | --- | --- |
| Source to review | spec +2 −1, lock 4 lines | SPEC.md 4 lines | SPEC.md 4 lines |
| Code changed | 23 lines in 11 files, 2 of them written by the model | 49 lines in 9 files | 55 lines in 8 files |
| Model work | 2 bodies, 27 s | 35 turns, $0.45, 67 s | 34 turns, $0.48, 71 s |

In philote, `record_swipe` went back to the model because it takes a Horse, and its body came back unchanged. HorseView's body changed in 2 lines.

## Result

Neither kill criterion holds. Fresh philote builds differ in 3% of lines, all inside model bodies, and the lock takes that to 0. Two Claude Code builds of the same prose differ in layout, code and behavior. With D-022, spec edits rebuild only the nodes that reach what changed. A feature change is a few spec lines to review, where an agent gives 50 or more lines of code. The bet in D-021 holds on this app. It hasn't been tested on a larger app, or on changes that the language can't express yet.
