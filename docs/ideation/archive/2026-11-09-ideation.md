# Strict spec compiler — ideation

Nov 9, 2026 · @Viljami

## Thesis

Code becomes a compile target. You write a strict, typed description of the app (entities, pages, components, actions). A compiler checks it, then uses an LLM as its backend to emit framework code. The generated code is machine code: never edited, pinned in a lockfile, and rebuilt only where the source changed.

Why strict objects instead of prose specs: prose specs drift and fill up with AI slop. A typechecked source can still be wrong, but it can't be vague. Ambiguity fails at compile time instead of turning into a guess buried in generated code.

The bet: the right level for AI codegen is a high-level language, not a chat window and not a Markdown spec.

## Principles

1. **The source is strict.** Every object has a type and a fixed schema. Unknown keys and free-floating prose are compile errors. Natural language is allowed only in named, length-capped fields (UI copy, a short intent hint).
2. **Generated code is machine code.** It lives in a build directory and is never edited by hand. Changes go into the source or into a native block (see Escape hatches).
3. **Determinism comes from the build system, not the model.** Every node's output is pinned by a hash of its inputs. Identical inputs never call the model.
4. **Verification comes from the source, not the LLM.** Types, routes, props and data shapes are checked mechanically against the source. A node that fails gets regenerated, or the build fails.
5. **Regeneration stays local.** Changing one node rebuilds that node only, unless its interface changed.
6. **Frameworks are backends.** Next.js is the first target. The same source should compile to a second framework without edits.

## Source language sketch

A whole blog fits in about 40 lines. The syntax below is a placeholder; the format is still open (see Open questions).

```
app blog {
  target: nextjs
  style: tokens/minimal
}

entity Post {
  title: string(max 120)
  slug: slug from title
  body: markdown
  published_at: date
  tags: [Tag]
}

entity Tag {
  name: string unique
}

page "/blog" {
  data: Post where published_at <= now order by published_at desc
  layout: list of PostCard
  empty: "No posts yet."
}

page "/blog/[slug]" {
  data: Post by slug
  layout: PostView
  not_found: 404
}

component PostCard(post: Post) {
  shows: post.title, post.published_at, excerpt(post.body, 160)
  links_to: "/blog/[post.slug]"
}

component PostView(post: Post) {
  shows: post.title, post.published_at, post.body as markdown, post.tags as chips
}
```

What the compiler can check before any model call:

- Route params exist on the entity they look up (`[slug]` → `Post.slug`).
- Component props match what the page passes (`list of PostCard` needs a `Post`).
- Queries only use declared fields, and `order by` fields are comparable.
- Every `shows` and `links_to` refers to something real.

What stays fuzzy on purpose: visual design goes through `style` tokens, and the exact layout inside a component is the backend's job.

## Compiler pipeline

&#91;embedded content: compiler pipeline · 8 stages, 1 retry loop\]

The compiler hashes each node and compares it with the lockfile. Clean nodes are copied from the store; dirty nodes go to the model, and each output must pass verification against the source before it is pinned. A node that keeps failing verification after a few retries fails the build, with the errors shown against the source line, not the generated code.

## Determinism model

Each node's output is keyed by a hash of everything that can change it. Same key means a cache hit: no model call, byte-identical output.

The cache key covers:

- the node's own source
- the interface hashes of the nodes it depends on (not their generated code)
- the backend target and its version
- the model id and its parameters
- the prompt template version and the compiler version

The lockfile maps each key to an output hash. Outputs live in a content-addressed store, like `/nix/store`.

- **Normal build:** regenerate only nodes whose key changed.
- **Frozen build** (`--frozen`, for CI): never call a model; fail if anything is dirty.
- **Upgrade** (like `nix flake update`): bump the model or backend on purpose, rebuild everything, review the diff.

This is pinned replay, not true determinism: a cached output is one sample, not the only possible one. Two things keep a changed node from drifting:

- the previous output is passed in as a reference, so the model makes a minimal edit instead of starting fresh
- verification against the source rejects any output that breaks the node's interface

## Escape hatches

The rule is never to edit generated code. When the language can't express something, you write a native block, the way C has inline assembly and `extern`.

```
native component Chart(points: [Point]) from "./native/Chart.tsx"
```

- A native block is a handwritten file with a declared, typed interface.
- The compiler never generates or touches it. It only checks that every use matches the declared interface.
- If you catch yourself wanting to edit a generated node, promote that node to native instead.

The ratio of native to generated nodes is a health metric: if most of an app ends up native, the language is missing something.

## Prior art

Nobody combines a strict typed source with an LLM backend and Nix-style pinned builds. The pieces exist separately.

| Project | What it is | How this differs |
| --- | --- | --- |
| [Tessl](https://codemyspec.com/blog/tessl-review) | Spec is the source, code regenerated from it | Its engine never left closed beta; testers got different code from the same spec, and it pivoted to agent skills in Jan 2026. Prose specs, no pinning |
| [CodeSpeak](https://groundy.com/articles/jetbrains-new-language-lets-you-talk-llms-specs-not/) | Markdown specs compiled to code by an LLM, from Kotlin's creator | Markdown, not a typed schema; no lockfile model that I found |
| [Spec Kit, Kiro, OpenSpec](https://particula.tech/blog/spec-driven-development-tools-spec-kit-vs-kiro-vs-tessl) | Prose spec first, then an agent writes code | Code is still the thing people edit, so specs drift |
| [artificer](https://rachittshah.com/posts/content-addressed-llm-builds/) | Content-addressed LLM builds with a lockfile and frozen mode | For processing text corpora, not codegen; no benchmarks |
| Wasp | A DSL for full-stack web apps that compiles to React and Node | Closest structural ancestor; no LLM, so every construct must be hand-written into the compiler (from memory, not re-checked) |
| Prisma, protobuf | Strict schema → generated code nobody edits | Proves people accept never editing generated code; covers data only |
| Nix | Content-addressed builds, lockfile, store | The build model to copy |

The main lesson from Tessl: nondeterminism killed regenerate-from-spec. Pinning and local regeneration are the direct answer.

## Open questions

- [ ] **Format:** a custom DSL (best error messages, more work) or an existing format like TOML, YAML or a Nix expression (free parser)?
- [ ] **How strict is strict?** Which fields may hold natural language, and how long can it be?
- [ ] **Visual design:** tokens only, or a design node that is generated once and pinned?
- [ ] **Scope of v1:** front end only, or data layer and auth too?
- [ ] **Node granularity:** page, component, or smaller?
- [ ] **Regeneration on change:** a fresh sample, or a minimal edit of the previous output?
- [ ] **Verification depth:** types and routes only, or end-to-end tests generated from the source?
- [ ] **The real value:** what does this beat "Claude Code + a SPEC.md + git" on? Candidates: retargeting, model upgrades, reviewing a 5-line source diff instead of 400 lines of code.
- [ ] **Compiler language:** Go or Rust?

## First experiment

One week, one blog, five checks. The point is to find out whether local regeneration and retargeting actually hold up, before designing a full language.

1. Write the blog above in the sketch syntax (2 entities, 2 pages, 2 components) and parse it with a quick parser.
2. Compile to Next.js with one model call per node. Verify with `tsc`, `next build` and a route check.
3. Add the lockfile and cache. A rebuild with no changes should make zero model calls and produce byte-identical output.
4. Change only `PostCard`. Only `PostCard` should regenerate, and the diff everywhere else should be empty.
5. Retarget the same source to a second framework (SvelteKit or Astro).

Measure: model calls per build, wall time, verification failures, and lines changed per source edit. Also make one feature change both ways (here, and with Claude Code on a plain repo) and compare.

**Kill criteria:**

- Step 4 can't stay local, because interface churn keeps breaking neighbouring nodes.
- Step 5 needs target-specific edits to the source.

If either happens, rethink the node boundaries before writing more compiler.
